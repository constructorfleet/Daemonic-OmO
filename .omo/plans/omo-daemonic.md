## TL;DR (For humans)

**Who this is for and what changes for them:** You and anyone you let sign in through your identity provider, each with their own omo account on this Mac. Instead of watching one project per terminal, you open one web page that shows every project's agents live and lets you start, steer and stop them, and put agents on schedules or loops.

**What you'll get:** A background service that starts at login and a web app on top of it. The app has your projects, live and past agent sessions with everything omo-agents shows today, task trees and workflow graphs, an agent launcher with steer/interrupt/close, cron-style schedules, repeat-until-done loops, an audit log and a kill switch. omo-agents moves into the same repo and keeps working from it.

**Why this approach:** omo already runs and supervises agents well, so the service never runs agents itself. It asks omo to open and steer sessions through omo's own scripting interface, and reads omo's files without ever writing them. Restarting the service or updating omo never kills an agent, and a probe flags any omo change that breaks the readers. Unattended runs work in separate git worktrees, so they never touch your working checkout.

**What it will NOT do:** It won't write omo's internal files, patch omo, or sandbox agents at the operating-system level (every agent runs as your Mac user). It won't show sessions from your other devices, offer web-based AI-provider login, or delete worktrees automatically.

## Execution strategy
### Run lifecycle (thread model)
This section supersedes the detail design (`.omo/reference/omo-daemonic-detail-design.md`) section 1 process fields (`pid`, `pgid`, `procStartedAt`, `exitCode`, `signal`, `runDir` supervision), section 2 "Process supervision" and `ps`-based recovery, section 3 cancel steps 2-3 (signals, `omo host stop`), and section 4 auth (bearer `/login?t=`, `SameSite=Strict`, loopback-only Host allowlist). Fire keys, decide/commit transactions, misfire/overlap/DST rules, the event ledger, SSE resume and the projector stay as designed.
- States: `queued -> creating -> active -> settled -> evaluating -> {closed | kept}`; terminal outcomes `succeeded | failed(create_refused | turn_error | host_unavailable | gateway_degraded) | cancelled | timed_out | lost(thread_missing) | skipped(overlap | queue_full | stale | worktree_cap)`.
- Create: unattended runs first get a daemon-created worktree (`git worktree add -b <branch> <path> HEAD` at `~/.omo-daemonic/worktrees/<projectId>/<runId|loopId>`, outside the user's checkout; branch `omo-daemonic/sched-<slug>-<runId>` per schedule fire, `omo-daemonic/loop-<slug>-<loopId>` per loop). Then `create({name: "odm-<runId>", cwd, model, reasoning, idempotency_key: "<fireKey>:<attempt>"})` with the run prompt inside `create` and no `permission_preset` (todo 5 assertion 2 proved a repeated create delivers its prompt exactly once), then commit the thread address.
- Session identity: the run stores `threadId`, `sessionId` and `sessionFile` resolved per spike assertion 3 (create/read field if exposed; else the unique `odm-<runId>` name located in the run cwd's session folder by glob).
- Completion: primary signal per spike assertion 6 (completion arm: bind `--events completion`, `report <thread> completion`, read the outbox row `outcome`); fallback signal = thread `state` running -> idle after the prompt's delivery plus a final assistant entry in the session tail. `settled` -> `evaluating` runs loop done checks; then unattended threads are closed (`close({graceful:true, wait_ms: 30000})`) and ad-hoc threads are kept until the user closes them.
- Timeout: at `activeAt + timeoutMs`: `interrupt`, then `close({graceful:true, wait_ms: 10000})`, then `close({force:true})` -> `timed_out`. Cancel: same sequence -> `cancelled`. Children that outlive the close (spike assertion 9) are listed on the run as `orphanChildren` until terminal.
- Slots: a run counts against per-project, per-user and machine caps only while its thread is `running` (or `creating`); a kept idle ad-hoc thread holds no slot.
- Permission mode and prompt delivery (decision gate resolved 2026-11-25): `create` carries no `permission_preset`; runs, audit rows and the UI record `permissionMode: "agent-dir-default"`. Todo 5 assertion 2 passed (a repeated create-with-prompt delivers once, with creator authority, while a `send` arrives as relayed external content), so the run prompt goes inside `create` under the create key instead of a follow-up `send`.
- Recovery on daemon start: `creating` -> call `create` again with the same idempotency key (reopens the same thread; a prompt inside `create` is not redelivered); `active` -> reconcile with `list` (missing -> `lost(thread_missing)`); `settled`/`evaluating` -> re-run evaluation once (guarded by `evaluatedRunId`). After an operator restart (the `omo daemon run --json` generation changed, or `sessionState` reports the hold) a reopened session is held `unattended` and an SDK `send` runs no turn (todo 5 assertion 7): for each nonterminal run, read `omo host session state <thread> --json`; if held, release it with `omo host session prompt <thread> <text>` where `<text>` is the run prompt when the session transcript does not contain it yet, otherwise the fixed text `Resume the interrupted task.` (the transcript check guarantees the prompt is never delivered twice; the release is audited); then re-apply `set_model` to the run's model (restore reverts it) and re-close every thread the daemon had closed that the restore listed again. `ensureHost` starts the operator with `--pinned` so idle exits never trigger this path.
- Degraded gateway (SDK cannot load or host cannot be ensured): new runs fail `gateway_degraded` / `host_unavailable` and the schedule's misfire/retry policy applies; the kill switch pauses all schedules and cancels all loops of the scope, refuses new spawns for that scope until released with `POST /api/v1/kill-switch/release`, and returns `uninterruptible: [runIds]` for runs it could not reach.
- Decision gate (recorded by todo 5 in `FINDINGS.md`): SDK for every run if assertions 1, 2, 4, 6 and 7 pass; SDK with idle+tail completion if only 6 fails; if the SDK cannot load in any runtime, or it loads but assertion 2 (duplicate suppression), 4 (preset names/application) or 7 (reopen after host stop) fails, STOP and escalate to the user (recovery and an `omo -p` engine both depend on these), never improvise. Resolved 2026-11-25: todo 5 stopped on assertions 4 and 7; the user chose the agent-dir default permission mode (no per-spawn preset) and CLI hold release plus a pinned operator for recovery, as written above; todo 27 records the upstream omo requests (an SDK creator permission-mode option and an SDK resume for `unattended` holds).
